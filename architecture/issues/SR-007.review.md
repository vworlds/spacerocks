# SR-007: Move Movement and Simple Physics to Server

## Objective

Move core Spacerocks movement and simple physics from the browser to authoritative server systems.

## Scope

- Migrate ship control input application.
- Migrate thrust, velocity integration, angular movement, friction, and wrapping.
- Use fixed shared world bounds instead of client canvas size.
- Mark modified network components after in-place mutation.
- Stop running these systems on the client.

## Dependencies

- `SR-005`
- `SR-006`

## Blocks

- `SR-009`
- `SR-010`

## Systems to Move

- `ShipControl`
- `Thrust`
- `Movement`
- `AngularMovement`
- `FrictionSystem`
- `Wrap`

## Implementation Notes

- Keep the original numeric feel first; do not redesign movement.
- Server simulation should use a fixed timestep.
- The current systems are frame-step based rather than delta-time based. Decide explicitly whether to preserve frame-step behavior or normalize using `dt`.
- If preserving feel matters most, initially run server at the original expected frame rate and keep constants equivalent.

## Acceptance Criteria

- Server moves ships and other moving entities.
- Clients see movement through mirrored `Position` and `Rotation`.
- Client no longer mutates authoritative movement components.
- Wrapping uses shared world bounds and behaves consistently for all clients.

**Must-fix:**
- `apps/client/src/systems/index.ts:2-8`: All six movement systems (ShipControl, Thrust, Movement, AngularMovement, FrictionSystem, Wrap) are still imported and registered on the client world. Acceptance criterion "Client no longer mutates authoritative movement components" is violated — these systems mutate Position, Rotation, Velocity, and Thrust on the client every frame. Additionally, the client-side `Wrap.ts` still uses `canvasSize` instead of shared world bounds. The client must stop running these systems to avoid overwriting server-authoritative state.

**Nits (optional):**
- `apps/server/src/game/movement.ts`: The `Thrust` and `FrictionSystem` systems mutate `Velocity` in-place without calling `entity.modified(Velocity)`. Since Velocity is not yet a network component this is harmless, but if Velocity is ever added to `NETWORK_COMPONENTS` this will break sync. Consider adding `modified()` calls defensively or documenting the assumption.
- `apps/server/src/game/movement.ts`: The `ShipControl` system doesn't call `entity.modified(Thrust)` after setting `thrust.active`. Same reasoning as above — harmless today since Thrust is not a network component, but fragile.

**Notes:**
- The server-side implementation of all 6 movement systems is well done: uses shared WORLD_WIDTH/WORLD_HEIGHT, calls `entity.modified()` on Position and Rotation, runs at fixed 60Hz simulation phase, and integrates with SR-006's `PlayerInputIntent` pattern.
- New server movement test file (`apps/server/tests/game/movement.test.ts`) has 5 tests covering input integration, velocity+friction, angular movement, wrapping, and input isolation — solid coverage.
- Client-side tests for the old movement systems still pass (14 tests across ShipControl, Thrust, Movement, AngularMovement, FrictionSystem, Wrap). These should be updated or removed when the client systems are disabled.
- No unrelated refactors or scope bleed detected. Dependencies (SR-005, SR-006) properly honored.
